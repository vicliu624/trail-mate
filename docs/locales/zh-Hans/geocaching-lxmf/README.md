## 2. 已确认的需求

1. Trail Mate 增加 geocaching 功能。
2. 藏宝点由用户分享，不依赖 geocaching.com 的账号、目录或数据下载服务。
3. 藏宝点发布与下载基于 Reticulum 上的 **LXMF 应用协议**；查询、响应和确认同样走 LXMF。
4. 当前只完成中文设计文档，放在 `docs/locales/zh-Hans` 下。
5. 完成设计并经用户评估通过后，才可以开始开发。
6. **藏宝点面向公共网络发布，不是单独分享给谁。任何支持本协议的 Reticulum 终端都能通过公共发现流程看到和下载，用户不需要先知道作者或选择接收方。**
7. **SD卡上的实际内容文件必须具有广泛兼容性，以GPX为主文件；不能只保存私有数据再把GPX作为以后可选导出。**
8. **项目GitHub Pages增加Geocaching世界地图板块，浏览器自己运行Reticulum/LXMF实时查询其他用户的公共标点，支持缩放、查看和GPX下载；不采用静态镜像或业务查询代理作为主方案。**

“任何终端都能看到”落实为公开可发现、无读者名单、兼容实现均可访问。裸 Reticulum 终端或不支持本协议的聊天程序不会自动获得藏宝点界面；网络分区、离线和物理不可达也不能被协议消除。这些可见性边界不得用来退回私人收件人模型。

“不依赖某网站”没有被扩展解释成“禁止 Reticulum 使用 IP 承载”，也没有被解释成“必须有公共目录服务器”。两者都不是用户已确认的要求。

## 3. 术语与边界基线

| 对象 | 负责的事实 | 不负责的事实 |
| --- | --- | --- |
| 藏宝点 `Cache` | 作者身份、稳定 ID、一系列签名内容版本 | 下载来源、聊天消息状态、某玩家是否找到 |
| 签名版本 `SignedCache` | 某作者对某一份精确内容的声明 | 宝藏现实存在性、全网最新性 |
| 目录摘要 `Summary` | 某来源在一个目录快照中的索引声明 | 尚未下载的作者原文的验证结果 |
| 公共目录节点 | 自动服务发现、内容收录、公共查询和目录复制 | 原作者身份、全网永久可达 |
| 内容来源 `Source` | 自动发现的公共目录及副本提供者 | 用户必须选择的私人接收方 |
| 发布请求 `publish` | 将公开记录提交给自动选择的公共入口并进入传播流程 | 对某位读者的定向分享、全网瞬间收到的保证 |
| 下载请求 `get` | 请求某端点提供指定点的指定或已知最新版本 | 下载地图底图、保证找到全网最新版本 |
| 本地副本 | 已通过对象验证并持久保存的内容 | 作者身份和修改权 |
| 个人寻宝记录 | 本机用户的找到、没找到、笔记 | 作者的维护状态、公开社区评分 |
| LXMF 消息 | 一次传递的外层消息及其身份、交付事实 | 标点唯一 ID、业务提交成功 |
| 应用请求 | 可跨 LXMF 重发关联的一次操作 | 分包序号、网络路由事实 |

必须避免的切法：把所有地图标点当成藏宝点；把传播节点当成目录；把来源当成作者；把外层签名当成经转发内容的原作者签名；把“已发送”当成“已保存”；把本地删除当成全网撤回。

## 4. 本稿提出、等待批准的范围

- v1 只覆盖公开、单地点、实体容器型藏宝点；每个点有一个作者身份。
- 使用可由任何人运行的公共目录网络；终端自动发现入口，目录自动复制，不要求所有玩家设备承担服务端。
- 支持文字、坐标、提示、难度、地形、容器大小和维护状态。
- 支持能力查询、公开发布、区域目录查询、详情下载、公共目录同步五个操作，以及服务发现 announce。
- 支持直达与传播交付下相同的异步请求语义。
- 个人寻宝记录只保存在本地，不定义公开日志协议。
- 支持公开传播，不支持私人读者名单、受限分享、访问撤销、群组加密权限。
- 不包含附件、多阶段谜题、共同作者、密钥轮换、逐点推送订阅、全网完整性证明及冲突自动合并。GPX主文件与必要的导入兼容已按用户要求纳入范围。

当前范围不追求复刻商业平台，但范围明确不等于设计完备。缺口与补全进度以09审计账本为准；不能把尚未定义的设备接口、恢复与命名问题留给编码阶段猜测。

## 6. 与现有项目约束的关系

依据[Reticulum 客户端架构](../../../reticulum_client_architecture.md)，Trail Mate 当前定位是客户端。本稿为公共目录定义完整服务职责，默认由独立端点承担；若某目标设备也提供目录，须承担全部 publish/query/get/sync 与保留义务，先评审并同步架构文档。不能让客户端角色限制变成定向分享产品模型。

依据[运行时所有权边界](../../../specification/RUNTIME_OWNERSHIP_BOUNDARY_FREEZE.md)，界面只提交意图、显示投影；不解析 LXMF 字节，不自行决定交付与持久化状态。未来应用协议必须复用现有消息交付、身份和去重事实，另行维护应用请求与签名对象事实，不能复制第二套底层消息账本。

本稿是新功能中文评审材料，按用户指定位置保存。没有修改上级目录的历史英文规范地位，也没有将内容放入被忽略的 `source/` 存档。
