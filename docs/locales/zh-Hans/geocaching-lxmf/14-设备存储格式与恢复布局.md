# 设备存储格式与恢复布局

> 本文已按GPX实际落盘要求修订：用户内容采用标准GPX，辅助日志不作为其他软件读取标点的前提。GPX字段与原作者扩展以[17](./17-GPX字段与外部编辑契约.md)为准；私有.gco主文件方案不再使用。本组设计仍在补全，尚未授权开发。

状态：待评审的具体存储候选，尚未实现或做介质掉电测试。适用：设备端公共客户端，不是公共目录服务器。日期：2026-09-15。

## 1. 选择与边界

首版候选使用**SD卡GPX主文件 + 辅助追加事务日志 + 双槽检查点**。GPX中包含标准可读字段与可选验证扩展，用户可直接复制文件；辅助日志保存请求、安装事务和个人状态，不是内容读取门槛。

核心只依赖11中的存储port；文件布局由平台适配器实现。已有[StorageOperationBudget](../../../../platform/esp/common/include/platform/esp/common/storage/storage_contracts.h)按逻辑工作项限制维护步长，[SD runtime](../../../../platform/esp/arduino_common/include/platform/esp/arduino_common/storage/sd_card_runtime.h)拥有挂载、外部块设备移交与文件IO。新业务参与这些机制，不私自挂卡或持锁阻塞UI。

本候选首版要求可靠可写的数据卷。ESP优先使用已挂载SD数据卷；未配置SD的目标不自动改写主题/固件Flash分区，在线写入功能标为存储不可用。若目标以后批准Flash数据后端，保持同一逻辑格式，另做写寿命和刷新保证验证。Linux可以使用平台提供的用户数据目录。挂载路径由目标装配传入，不写死在核心。

## 2. 物理布局

```text
<data-volume>/trailmate/geocaching/
  caches/<完整cache_id小写hex>.gpx
  imports/                                 # 保留用户输入原文件
  exports/                                 # 用户明确生成的批量GPX
  .state/
    format.bin
    history/<完整revision_hash小写hex>.gpx  # 有保留义务的历史和签名证据
    journal/<16位小写hex序号>.gcj
    checkpoint/a.gcs
    checkpoint/b.gcs
    staging/                               # GPX临时文件与安装备份
```

用户主文件按cache_id命名，每个点一个wpt；历史GPX按revision_hash命名。路径只由固定长度ID/hash与本机序号生成，不使用远端名称或相对路径。原签名对象上限4166字节是网络/内层约束，GPX文件上限65536字节包含XML转义和Base64开销，不能混用。边界计算见17 §7。

草稿、请求、个人记录、版本元数据、候选目录缓存都作为事务日志中的逻辑键值保存；因此08中的drafts/requests/personal是职责划分，不要求各建一个独立可不一致的物理目录。本文物理布局取代那份未冻结的目录示意。

format.bin保存根格式头：ASCII `TMGC`四字节、format_version uint16=1、header_bytes uint16=28、volume_instance bin[16]、CRC32四字节；数值均大端。CRC覆盖前24字节。volume_instance在格式首次创建时生成并持久保留，不是作者Identity。未知格式只读拒绝，不自动初始化覆盖。

## 3. 公共文件记录包装

仅辅助.gcj记录和.gcs数据块采用以下包装。GPX必须是普通XML文件，不能在前面添加本包装，否则其他软件无法直接读取：

| 字段 | 长度 | 含义 |
| --- | --- | --- |
| magic | 4 | ASCII `GCR1` |
| kind | 1 | 2事务、3检查点页、4检查点尾；1保留不用 |
| flags | 1 | v1固定0 |
| header_bytes | 2 | 固定24 |
| payload_bytes | 4 | 后续payload长度，≤65536；更小的类型上限同时适用 |
| sequence | 8 | 事务序号或检查点基准序号；对象为0 |
| crc32 | 4 | 覆盖头前20字节与payload拼接，不含本字段 |
| payload | 可变 | 下文指定内容 |

数值大端。CRC采用CRC-32/ISO-HDLC（反射多项式0xEDB88320，初值与最终异或均0xFFFFFFFF）；只用于损坏检测，不取代作者签名。类型/长度/CRC不合法立即停止解析该记录，不按伪造长度分配内存。

GPX读取按17核对XML字段、扩展、原作者签名和文件身份。文件SHA-256用于替换与外部编辑检测，revision_hash用于原作者内容版本，两者分别保存。不能以文件hash变化直接判断作者分叉，也不能因索引标记已验证而跳过外部文件修改检测。

## 4. 事务日志与逻辑键

每个kind=2记录是一个完整事务，payload使用CMP1：

```text
[store_schema=1, previous_sequence:uint64,
 mutations:[[table:uint8,key:bin[1..96],value:bin[0..32768]或nil], ...]]
```

单事务最多64个mutations，整体payload≤65536；同一事务不允许重复(table,key)。value=nil表示删除逻辑键，空binary是合法空值而不是删除。只有完整记录CRC通过、previous_sequence衔接、schema合法且引用对象可验证，才算提交事实。

逻辑键对应的value必须为应用模式定义的CMP1数组，不能把C++结构体原始内存写盘。各表含义：

| table | 键 | 值的逻辑字段（固定顺序） |
| --- | --- | --- |
| 1 ObjectRef | revision_hash 32字节 | `[cache_id,revision,previous_hash,state,created_at,verified,retained_until]` |
| 2 CacheHead | cache_id 32字节 | `[current_hash或nil,conflict_state,install_generation,highest_seen_revision]` |
| 3 AuthorIssued | cache_id+revision大端4字节 | `[revision_hash,identity_public_key,issued_at]` |
| 4 Draft | 本机draft_id 16字节 | `[author_identity_ref或nil,base_hash或nil,draft_fields,edit_generation]` |
| 5 Outgoing | 本机source16+destination16+request_id16 | `[custom_data,state,continue_intent,task_id,install_generation或nil,created_time,terminal_data或nil]` |
| 6 IncomingResult | source16+local_destination16+request_id16 | `[wire_version,fingerprint,response_data,accepted_time,retention_deadline]` |
| 7 Personal | cache_id 32字节 | `[result,reference_hash或nil,note,updated_time]` |
| 8 Candidate | 发现destination16 | `[delivery16,public_identity64,epoch16,sequence,health,last_seen,last_success,backoff_until]` |
| 9 SummaryCache | delivery16+cache_id32 | `[summary,snapshot_id16,received_time]` |
| 10 Task | 本机task_id16 | `[task_kind,cache_id或nil,revision_hash或nil,state,continue_intent,child_request_keys]` |
| 11 LocalProof | cache_id32 | `[proof_hashes,history_pending_hashes]` |
| 12 GpxInstall | 本机transaction_id16 | `[cache_id,revision_hash,new_file_sha256,old_file_sha256或nil,install_generation,phase]` |
| 13 TxAttempt | Outgoing键48字节+本机attempt_id16 | `[lxmf_hash或nil,state,submitted_time,finished_time或nil]` |

Outgoing同时保存最大8192字节请求与最大8192字节响应，必须再计入数组、bin头、task_id和时间等开销，因此单value上限从原16384修正为32768。单事务仍≤65536，编码前预估，不允许拆开一个必须原子成立的业务提交来迁就空间。

TxAttempt.state=0Accepted、1InFlight、2Delivered、3Failed、4CancelledBeforeSend；lxmf_hash为nil或完整32字节，attempt_id为本机CSPRNG标识，不等于request_id。重启恢复后即使栈已无该尝试，也保留记录为历史事实，不用旧hash冒充新投递。

GpxInstall.phase=0 Prepared、1 Installed、2 ConflictExternal、3 RolledBack。临时和备份路径由transaction_id派生；表中不得接受远端提供的任意路径。Prepared表示新GPX已在staging完整耐久且验证，Installed表示目标GPX已完整可读取且对应generation仍有效。

GpxInstall兼容六字段旧记录；完成目标验证及历史文件保留后，可追加第七字段整数`1`，表示后续文件处理也已完成。该字段只允许出现在Installed阶段。没有此字段的旧记录或中断记录仍参与恢复；有此字段的记录不再在启动时重复读取GPX。恢复旧记录时，同时从已保存的签名内容补齐列表索引字段，再原子提交最终完成标记。

字段中的wire对象直接引用01/04的固定结构。draft_fields按CacheRecord中的可编辑字段顺序保存：`[state,latitude_e7或nil,longitude_e7或nil,name,description,hint,difficulty_x2,terrain_x2,container_size]`，其文本仍遵守协议长度，空草稿允许name为空，签发前须完整验证。identity_ref为完整公共身份64字节，不存私钥。

本地枚举分配：verified固定1（未验对象不得写table1）；conflict_state=0正常、1历史待核实、2已证实冲突；Personal.result=0未记录、1找到、2未找到。Task.kind=1发布、2下载、3查询、4检查更新。请求state=0Queued、1InFlight、2AwaitingResult、3Unconfirmed、4RemoteResultRecorded、5LocalSaveFailed；task.state=0等待、1进行、2部分完成、3完成、4受阻、5停止。continue_intent均为整数0/1。

时间字段统一为`[boot_id16,monotonic_ms:uint64,utc_seconds或nil,utc_trusted:0或1]`；deadline为同结构的可信UTC期限或nil，nil时按10 §6保守保留。不能把deadline=nil解释成已过期。generation为uint64。child_request_keys最多3项（公开发布），下载批次由父界面分组多个task，不把20项塞进发布子请求字段。proof_hashes最多2项；history_pending_hashes最多2项，更多疑点保留摘要诊断而不无限扩张。

Candidate.health=0Candidate、1Ready、2Backoff、3Quarantined、4Incompatible、5Expired，与12状态对应。health是本地事实，不发送。note为UTF-8文本≤2048字节，draft与note控制字符规则同描述。

### 4.1 各字段的补充约束

- 所有cache_id、revision_hash、file_sha256、fingerprint恰好32字节；identity_public_key/identity_ref恰好64；本机task/draft/transaction/attempt/boot_id恰好16。空bin不代替nil。
- ObjectRef的revision、previous_hash、state、created_at与01记录一致；retained_until是下面定义的deadline，不是作者时间。CacheHead.highest_seen_revision为uint32，0仅代表尚无已验版本；current_hash=nil只在未安装或无法选择当前时合法。
- Outgoing.custom_data为1..8192字节且是完整原请求；terminal_data为nil或1..8192字节完整响应；RemoteResultRecorded必须有terminal_data，未终态不得伪造响应。请求身份与表键里的source/destination/request_id一致。
- IncomingResult.response_data为1..8192字节，其fingerprint为原CUSTOM_DATA的SHA-256；wire_version=1。该表只服务客户端支持的入站capabilities；不因表存在就宣告目录服务。
- 时间tuple的utc_seconds为nil或0..253402300799；utc_trusted=1要求utc_seconds非nil。deadline采用相同tuple，但表示未来截止点；无可信期限时nil并保守保留。Candidate.last_success可nil；last_seen必须存在；backoff_until可nil。已完成attempt要求finished_time非nil。
- Task.child_request_keys每项恰好48字节并引用Outgoing；查询/下载超过三次来源尝试需显式新任务或结束，不能悄悄超出表上限。task_id与Outgoing父引用必须互相一致。
- Draft.base_hash可nil；坐标未填写时lat/lon同时nil，不能只有一项有效。generation初值1，递增不回绕；用尽必须拒绝创建新的意图，不能复用旧generation。
- SummaryCache.summary是01的Summary，键cache_id与摘要一致；snapshot_id16与来源分开。LocalProof数组不得重复hash，proof_hashes为空或两项，单项不足以表达已证实二记录冲突。
- 未知table、额外数组项、未知枚举、断裂外键或值超限导致恢复失败/只读诊断，不使用默认值静默修补。索引可重建，作者原文和任务事实不能凭空补造。

上述为首版客户端所需表；公共目录额外的全量sync日志/快照表不在设备客户端格式中，不能据此声称目录服务实现已完整。新增本地表/值字段须提升store_schema并提供迁移，不能用尾部可忽略字段偷改含义。

## 5. 提交算法

1. 存储owner串行验证预期head/install_generation与容量，分配下一个sequence；不持锁等待网络。
2. 从有效签名记录生成完整GPX，写同卷staging、刷新、关闭、重新解析验签并核对所有映射；计算new_file_sha256。
3. 读取当前主文件，核对old_file_sha256与用户安装generation。若外部已修改，记录ConflictExternal并保留用户文件，等待明确处理，不后台覆盖。
4. 追加并耐久提交Prepared安装意图，记录旧/新hash。旧GPX移到事务备份路径；已有历史保留义务的旧签名版本同时保留为history GPX。
5. 把完整新GPX安装到caches目标位置，刷新并重新核对new_file_sha256及签名映射。不得假定rename天然抗掉电。
6. 追加Installed事务，将对象版本、来源、请求结果和安装generation共同提交。此后才发布snapshot与下载成功；没有Installed不能显示可恢复的完成。
7. 新GPX与Installed均耐久后清理无保留义务的备份和孤儿staging。其他无需GPX替换的事务仍按完整单记录提交。

Prepared与Installed之间是可恢复的文件安装协议，不是对两个文件系统操作假称原子。启动时先恢复所有Prepared：新文件hash匹配则在重新验证generation后完成；旧文件/备份完整则回滚或继续安装；两者都不可信则只读报错。不会把缺失主文件当成用户有意删除。

### 5.1 Prepared恢复的确定分支

先比较已持久CacheHead.install_generation与安装意图，再检查文件hash。不能只看到新文件完整就完成一个已被用户取消的安装。

| generation与文件状态 | 必须动作 |
| --- | --- |
| generation匹配，新目标hash匹配且完整验证 | 补提交Installed，复原结果，不重复安装 |
| generation匹配，旧目标仍完整，新文件只在staging | 可以续安装；保留旧目标直到新目标确认 |
| generation匹配，目标缺失，旧备份完整 | 先恢复旧目标保证可读，再恢复/重试安装 |
| generation已失效，目标仍为旧文件 | 终止旧安装，记录RolledBack；执行当前删除/新安装意图 |
| generation已失效，目标为该旧安装的新文件 | 仅在hash仍匹配该事务时移出活动caches；不得因此恢复已被用户明确删除的旧副本 |
| 任意generation，目标与old/new两种hash都不符 | 当外部编辑保留，不删除、不自动回滚覆盖；记录ConflictExternal |
| 目标与备份皆损坏且无法证明文件归属 | 保留证据，ReadOnly/Corrupt，不覆盖成空文件 |

删除或新安装意图拥有更新generation，决定活动caches应保留什么；旧事务恢复只清理自己可证明拥有的临时/目标内容。不要把“回滚”实现成无条件复制旧备份，否则取消后可能复活用户已删除文件。

平台无法确认刷新/关闭/目录项的耐久顺序时必须返回Unavailable，不得把普通write成功当Committed。FAT/SD掉电行为必须在实施阶段验证；本文不假设rename天然原子或介质永不丢写。

## 6. 日志段、检查点与恢复

journal段上限1MiB，单记录不跨段；不足容纳下个记录时新建下一段。段文件名按首个事务sequence命名。发现尾部不完整记录时，保留前缀且停止在该处，不扫描后方magic尝试拼接“恢复”；后续连续段若存在但前置链损坏，进入Corrupt/只读，不能跳过已损坏的已提交中段。

检查点.gcs是按(table,key字节序)排序的逻辑键值完整快照，kind=3页payload=`[page_index,entries]`，entries为`[table,key,value]`，每页payload≤65536。单value上限32768，必须整项放入一页；不能把一个逻辑值跨页切碎。page_index从0连续递增。尾kind=4 payload=`[page_count,entry_count,SHA256(所有kind3完整包装字节拼接)]`。所有页sequence相同，代表已包含的事务sequence；无尾记录、页顺序不连续或digest不符则整份检查点无效。

写检查点时保留旧有效槽及其所需日志：先向staging写完整新文件并验证，再替换较旧槽。启动选两个槽中完整有效且sequence最大的一个；同sequence不同digest判损坏，不按文件时间择优。新槽验证耐久前不能删除旧槽或必要日志。

恢复顺序：验证辅助format/volume_instance → 选择有效checkpoint → 重放完整事务 → 恢复Prepared GPX安装 → 校验GPX及映射/文件hash → 恢复未完成请求和generation → 输出状态。缺失必要日志不当空任务账本初始化；但用户仍可在其他软件读取独立GPX。

仅复制GPX而没有.state时，可明确启动“重建内容索引”：扫描并验证GPX恢复内容，旧任务/个人记录/防回退历史无法从文件凭空恢复，界面说明这一差别。辅助数据损坏不允许自动删除可读GPX来恢复空库。

压缩只在新检查点完整耐久后回收≤该sequence且不再为旧槽恢复所需的日志；至少保留一个完整可恢复基线。具体删除顺序须保持另一槽可恢复，不能同时删掉两条恢复路径。

## 7. 挂载、拔卡与卷变化

Hydrating期间不接受持久发布/安装，UI显示加载中。拔卡或外部USB块设备取得所有权时进入Unavailable，停止新写；正在进行的事务由存储owner给出失败/未知完成，重新挂载后必须恢复核实。

volume_instance改变意味着插入了另一个数据卷。旧卷的未完成对象安装句柄全部失效；不能把新卷同名路径当原请求结果。用户看到“数据卷已更换”，重新建立该卷会话。作者身份仍在既有identity owner中，不能因新SD卡自动生成新身份。

只读卷允许浏览已验证且可读取的历史，不允许显示新下载保存成功。格式未知、CRC损坏或磁盘结构不连续时保留原文件；不自动格式化或清空以恢复功能。

## 8. 数据删除、升级和恢复能力

普通删除已下载点：先事务提升install_generation并移除安装引用，再GC无保留需求的正文；保留个人记录、作者签发账本、防回退元数据和冲突证明。用户明确清空全部寻宝数据才清除这些，并说明不等于全网撤下。

store_schema升级必须使用另一份staging迁移数据，验证完整后发布新格式，保留旧可恢复数据直到新版本确认；未知较新版本只读拒绝。首版没有定义向旧固件写回降级转换，不允许旧固件“修复”新格式。

目录原文不是签名密钥备份。备份本目录只恢复内容和本地账本，作者私钥按现有身份备份机制单独处理；缺失私钥可以阅读但不能继续签发。

## 9. 存储验收

| ID | 场景 | 期望 |
| --- | --- | --- |
| DSK01 | 对象已落盘、事务未写即掉电 | 孤儿不显示已安装，可回收 |
| DSK02 | 事务尾记录只写一半 | 恢复完整前缀，不扫描假magic |
| DSK03 | 日志中段CRC坏而后续有数据 | Corrupt/只读，不跳过坏段显示成功 |
| DSK04 | 写新checkpoint时掉电 | 旧槽和必要日志仍能恢复 |
