# 检查点轮换与设备会话接入

2026-09-24，本记录描述当前工作区主机验证，尚未刷入 L2。它不代表长期日志回收或掉电验收完成。

## 实际接入

`browse_runtime.cpp` 在查询达到 PageReady、没有前台发布/下载/草稿保存、没有其他工作区持有者时，每累计 256 次序列增长尝试检查点轮换。维护器还完整验证磁盘检查点，只有当前序列相对最近检查点至少增长 256 时才修改文件，避免新会话重复重建近期检查点。

轮换使用原有公共存储 owner，一次调度只推进一个有界步骤。复用会话的 8 KiB 读取缓冲和 8 KiB 编码缓冲；排序阶段将后者用作 32 条索引引用的排序区，导入阶段将其用作记录比较区。没有在设备任务栈上放置完整账本或增加常驻最大缓冲。

`SdCheckpointRotation` 完成以下流程：

1. 完整验证两个现有检查点，检查增长阈值；不足阈值时不修改文件。
2. 将已验证的当前根同步到另一个根副本并回读确认，扫描检查点引用，选择未被引用的目标槽位并保留可恢复的旧检查点。
3. 对有效索引引用执行固定内存的磁盘归并排序，再逐条读取值，生成并回读临时检查点。
4. 仅替换没有被当前根引用的检查点槽位，再完整验证发布后的文件。
5. 清理两个根都不引用的索引槽位，复用已有检查点导入、引用验证和双向逻辑等价比较。
6. 发布新索引根，将另一个根同步到它，最后清理已不再被引用的旧索引槽位。

退出会话可以中断维护；先释放维护对象和工作区，再由下次启动恢复处理落盘状态。此退出分支已接入，针对所有写入阶段的中断测试尚未完成。维护失败后禁止继续使用旧借用视图执行业务写入。

## 维护期间分页补充

维护期间的 `loadMore()` 现在只记录一个绑定当前页面版本的分页意图，不在 UI 回调中提交存储请求。维护让出后，由存储 worker 在工作区空闲时重新检查页面版本及分页游标，再提交请求。重复点击返回未受理，排队期间隐藏可继续分页状态；刷新改变客户端阶段或页面版本后，旧意图不会直接提交。

实际会话回归新增了带游标的第一页与空的末页：先观察旧临时文件被删除、重新创建，确认本轮维护确实运行，再点击分页。验证重复点击不被接受、UI 回调没有存储访问、分页请求只发送一次、第二检查点尚未发布、末页被持久化并恢复可刷新状态。测试通过。刷新取消旧意图的判断已实现，尚未单独增加对应交互场景。

## 索引扫描减少重复查找

`SdIndexScan` 原来对分片中每个引用都重新执行最新版本查找。改动利用逆序扫描已具备的证明：分片末条记录必然是该键最新引用；相邻的同键较旧引用必然已被覆盖。当前记录缓冲保留前一条引用，读取下一条时复用已释放的值工作区，不增加扫描器成员或整表缓存。小于 152 字节的调用者工作区仍走原有同键查找路径。

每条引用仍检查完整 CRC、卷标识、表、桶和序列顺序；首次遇到的有效值和删除记录仍执行原来的值读取验证。非相邻同键及同桶异键继续使用完整查找。

`geocaching_index_scan_history` 使用两个不同但同桶的键、60 个旧版本、交错更新和最终删除，比较 144 字节工作区的回退路径与正常工作区：分别 745 和 273 步，输出一致。破坏被覆盖的最旧索引记录 CRC 后，两条路径都拒绝损坏数据，没有恢复已删除记录。

## 跨会话阈值与发布中断重试补充

增长阈值判断已提前到第一次根同步之前。两个全新维护器分别读取同一个近期检查点，都结束为 Complete，磁盘文件、目录集合及两份根内存与开始前完全相同。实际会话测试在第一次维护后新增 256 次真实提交，再验证下一会话的维护、草稿抢占和分页抢占，继续通过。会话仍按尝试序列节流，因此阈值代表开始维护的最低增长量，不保证恰好第 256 次提交立即运行。

另修复“检查点已发布、索引未替换”后永久 Deferred 的路径。若通常选择的旧槽位仍被当前索引引用，而另一槽位未被引用，维护器保留经过完整验证的被引用旧检查点，重用未引用槽位。测试在新检查点发布后立即让出，继续提交新记录，再创建新的维护器；重试完成，最新序列保留，被引用的旧检查点内容未改变。

截至上述阈值修复阶段尚未删除日志；后续回收接入如下。全写入阶段掉电/拔卡、实机空间和共享 SD 延迟仍是待完成项。

## 日志回收接入（2026-09-24）

实际会话使用的 `SdCheckpointRotation` 在新检查点验证、双根同步和旧索引清理之后接入 `SdJournalReclaim`。第一次轮换没有可保留的旧检查点时不删日志。后续轮换先验证从旧检查点到当前序列的日志连续性、完整帧 CRC、事务格式和行形状，再逐段验证并删除完整覆盖于旧检查点之前的日志；跨越边界的分段完整保留。仍复用会话工作区，不加载文件列表或账本。

回收期间遇到外部占用或卡不可用，轮换器停止推进；恢复访问后要求正常索引恢复，不把先前的检查点证明用于删除，也不向前台交还未经重新验证的根。独立回收器遇到外部占用后会重新证明日志后缀，但其调用契约仍要求调用方保证保留检查点的有效性。

新增 `geocaching_journal_reclaim` 覆盖跨界多记录分段、缺失/CRC 损坏/截断的恢复日志，以及首次删除前逐步插入外部占用和同卷篡改。验证后缀未证明时不删除文件、没有被占用期间的 I/O、句柄释放及每步传输不超过 512 字节。此字节约束不代表真实 SD 延迟保证。

轮换集成测试连续三轮确认覆盖日志被回收、必要后缀不变。每轮进一步破坏新检查点，再使用生产 `SdIndexRepair` 从旧检查点与保留日志恢复，最终事务序列与回收前一致。实际 `browse_runtime` 主机集成回归也通过。尚未穷举每次文件删除时的掉电，也没有将本轮变更刷入 L2；本机仍未枚举到 COM67。

## 本地读取开销定位

设置 `TRAIL_MATE_TEST_IO_PROFILE=1` 后运行 `geocaching_browse_runtime`，每段验收等待会输出成功读取的总字节数、不同文件数和读取最多的五个文件。统计仅存在于主机 SD 替身；不修改设备固件，不计算失败读取、元数据操作或真实总线耗时。各等待段单独清零，方便使用相同业务样本比较优化前后。

当前较长历史场景中，交付能力响应到查询派发读取 461,090 字节、62 个文件，其中 `checkpoint/a.gcs` 累计读取 143,133 字节；对应 16,613 tick。更早的分页场景同一阶段读取 282,788 字节、46 个文件。能力响应已通过测试传输接口同步交付，所以这段等待测量的是本地处理和持久化推进，不能归因于目录没有回复。

代码核查发现 `SdIndexedCommit` 对涉及表 5、10、13 的变更启动 `SdIndexReferences`，后者扫描所有现存请求、任务、尝试记录并读取关联记录。这是明确的重复读取来源，但仅凭按文件统计尚不能把全部耗时归因于该类。后续应以同一场景测量调用阶段，审计已验证父状态下的增量校验或读取复用；不得直接跳过引用验证来换取通过速度。开启统计后的完整会话回归通过。

## 发送准备避免重复读取正文

`IndexedDispatchStore::readForSend` 原先按“请求 → 所属任务 → 同一请求”读取，第三次读取仅为恢复被任务读取覆盖的正文。现在将第一次已验证的请求正文暂存在此阶段空闲的编码工作区，再检查所属任务；确认关联和继续意图后直接返回暂存正文。已有派发器同步消费正文后才开始下一次持久化，因此租约不跨越后续编码操作。仅增加一个长度字段，不增加消息缓冲。

工作区不足、与读取帧或根元数据重叠时，仍走原来的请求重读路径。专项测试使用真实索引和已持久化的发送尝试，比较普通、小容量和重叠工作区，要求正文逐字节相同、释放 owner 和文件句柄，并在任务停止后返回 stopped 且不提供正文。普通路径读 964 字节，两个回退路径均读 1,446 字节。实际会话回归（含最大草稿字段发布、下载、恢复）通过，耗时约 25 秒；这不是设备端时延结论。测试入口尚未收录进 GitNexus，风险分析为 UNKNOWN；生产方法图谱风险为 LOW，但虚调用者需通过源码补充确认。
