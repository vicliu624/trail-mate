# TMAP 固件资源约束

TMAP 可以有数十 GB 的文件体积，但设备内存占用必须有固定上限，不能随文件体积、POI 数量或已安装地图包数量无限增长。本文约束固件接入；尚未接入的项目标记为设计要求，不能当作设备端已完成的能力。

## 当前读取核心

`modules/core_tmap` 的 `Reader` 不进行堆分配，也不持有瓦片像素；由调用方提供 `Workspace`、搜索游标和输出缓冲。

| 对象 | Windows / ESP32-S3 编译确认 | 编译期上限 | 设备放置要求 |
| --- | ---: | ---: | --- |
| Reader 控制状态 | 120 B | 192 B | 小型长期对象，避免重复实例 |
| Workspace | 13,000 B | 16 KiB | PSRAM；一个地图工作线程共享一个 |
| 其中索引页缓存 | 8,192 B | 两页，每页 4,096 B | 包含在 Workspace 内 |
| SearchCursor | 792 B | 1 KiB | PSRAM，最多一个活动查询 |
| 256 × 256 RGB565 瓦片 | 131,072 B | 128 KiB / 张 | 调用方提供的 PSRAM 缓冲 |
| 256 × 256 RGBA 瓦片 | 262,144 B | 256 KiB / 张 | 按需提供，不能永久为所有瓦片预留 |

这些尺寸包含类型对齐，但没有包含 SD 驱动、任务栈、事件队列、LVGL 缓存等成本。使用实际 ESP32-S3 GCC 8.4 工具链确认了同样的对象尺寸；设备运行时高水位仍需单独测量。

ESP32-S3 的 `-Os -fstack-usage` 结果显示：`readPoi` 单帧 64 B、`searchStep` 单帧 96 B、搜索初始化单帧 144 B、`visitAnnotations` 单帧 240 B。读取核心最大单个栈帧是 240 B；完整栈需求还包括调用链、空间树递归、回调和 SD 驱动，不能把 240 B 当作任务总栈占用。

核心访问模式：

- 只读取当前索引页和命中的数据；不加载完整目录树、POI 表、名称字典或倒排列表。
- 最多缓存两页，缓存置换不分配内存。
- POI 和名称使用固定工作区，访问回调只借用数据；回调若保留结果，必须复制到受限的结果列表。
- 搜索只保留最多八个倒排列表引用，按名称记录检查交集，不展开完整列表。
- 搜索初始化也可续执行，每次 `searchStep` 的工作预算最多为 64 个初始化索引项或候选名称。该预算限制工作单位，不承诺固定耗时；一次索引项访问仍可能读取多页，SD 忙时返回 `Busy`。
- 搜索游标直接在调用方存储中构造，避免生成一个游标大小的任务栈临时对象。
- 文件偏移、长度和 POI 行号使用 64 位值；不通过装入内存来规避大文件访问。

## ESP 接入的硬约束与实现状态

当前已接入地图工作线程、原生像素事件/显示所有权和 Arduino ESP32 的独立标注流程。地图源新工作区、目录条目、工作缓冲和原生像素显式分配到 PSRAM。整改前世界/中国两个包共用的工作区和目录为 18,856 B（独立源验证程序）；本次会话模式整改增加 1,024 B 缩放候选位图、16 项固定定位缓存及循环替换下标，新增内存均在源 State 的 PSRAM 分配中。定位项只保存坐标键、包编号及 offset/length/CRC/codec，不保存像素。目录每 16 个条目扩容，最多 256 个包。

工作缓冲固定为 256 KiB，兼容最大的 v1 RGBA 瓦片。所有原生像素的在途事件与显示缓存共享 3 MiB 上限，包含像素所有权头；预算不足时返回可重试事件。显示描述符共用事件像素，RGBA 通道转换原地执行。工作线程退出后释放包目录、读取工作区及工作缓冲。

本次续读/预取整改增加以下有界 PSRAM 状态：两个按需分配的 4 KiB SD 块及少量控制字段；三个 AnnotationCursor（每个编译期上限 1 KiB）；最多三个按需分配的标注载荷，每个 `sizeof(TileHeader) + 200 × sizeof(Record)`，按既有类型上限合计不超过约 132 KiB。这些是新增标注暂存预算，不能计入原生像素 3 MiB 后便认为已覆盖全部内存。无活动地图时全部释放。

像素续读借用原有 worker scratch，不增加第二份 128/256 KiB 工作缓冲。预取最多四块，只占原有像素和图像对象缓存，不扩大 3 MiB 预算；可见底图优先，最多一个屏外预取在途，像素余量不足两张最大 RGBA 瓦片时停止发起预取。标注布局仍沿用原有可见区域与 8/16/24/32 个文字标签上限。

上述数值是 TMAP 子系统的部分预算，未覆盖整机、旧 PNG 解码及其他页面。搜索 UI 和跨包结果调度尚未新增，因此下面的 Top-K 约束仍是其后续接入要求。

### 内部 RAM

大块 TMAP 工作区、目录存储、结果列表和像素缓冲必须显式申请 PSRAM。申请失败应返回可恢复的资源不足状态，不能自动改用内部 RAM。少量控制对象、同步对象以及 SD/SPI 驱动必须的内部或 DMA 缓冲，可以使用内部 RAM；需逐项计入总预算。

禁止在地图任务栈上创建 Workspace、搜索游标、大型 POI 数组或像素数组。CRC 查表应存放在只读区。必须核查已有分配函数的内部 RAM 回退行为，不能仅凭函数名包含 PSRAM 就认为满足要求。

### PSRAM 同样需要控制

PSRAM 容量也有限。像素预算应覆盖所有同时存活的缓冲：工作线程输出、待处理事件、LVGL 已缓存瓦片和临时转换缓冲。不能只计算一张瓦片。

以 RGB565 为例，16 张缓存本身就需要 2 MiB，尚未加上工作缓冲及事件队列。接入时必须根据目标硬件确定总像素预算，并使缓存容量、队列容量及在途任务共同遵守该上限。RGBA 瓦片占用翻倍，必须按实际字节计费。

尽量让已发布像素的所有权直接交给显示缓存；不要为同一张原生像素同时保留工作输出、事件拷贝和显示拷贝三份完整内容。淘汰缓存或丢弃事件时立即释放像素。不能为了避免一次拷贝而无限延长缓冲生命周期。

### 地图包与查询

多包目录仅保留有上限的元数据，不为每个文件建立独立页缓存。串行复用一个 Reader 和 Workspace，打开文件数量固定。目录达到上限应明确报告容量状态，不能静默漏掉地图。

搜索结果采用固定 Top-K 容量，按完整 128 位稳定 POI ID 去重，不能收集全部命中后再排序。取消查询、离开地图、SD 介质切换及 USB 接管时释放或失效相应资源。SD 忙时重试，不将临时失败写入永久缺失缓存。

### I/O 与原生像素

读瓦片使用已有 SD 运行时的 64 位随机访问接口。页读取和像素传输放在地图工作线程，不能在 LVGL 线程阻塞执行。

RGB565 原生瓦片可以省去 PNG 解码，但仍需要索引读取、像素读取和 CRC 校验。RGBA 若与 LVGL 要求的通道顺序不同，需要有界的原地转换；不能宣称所有格式都完全无需处理。PSRAM 不能直接满足某些 DMA 外设要求时，应使用受限的小块内部缓冲，不能复制整个瓦片到内部 RAM。

## 真机验收仍需记录的数据

固件在已有地图性能报告中追加 `[GPS][MAP][memory]` 行，约每五秒且有事件时输出：原生像素当前预算占用、内部 RAM/PSRAM 当前余量、各自自启动以来的最小余量，以及地图工作任务测得的最小剩余栈字节数。栈值由工作任务自身采集，避免从 UI 使用已经退出的任务句柄。堆最小余量包含其他子系统，不代表 TMAP 单独造成的峰值；需要与地图打开前的基线一起解释。

1. ESP 编译得到的对象尺寸与栈帧使用；运行时任务栈高水位。
2. 冷启动、地图打开、连续拖动、缩放、多包切换和搜索时的内部 RAM / PSRAM 当前值及峰值。
3. 总像素存活字节数、缓存数量、事件队列峰值及正在进行的读取数。
4. PSRAM 分配失败、队列满、搜索取消、SD 拔出及 USB 接管后的释放和恢复行为。
5. 同一操作反复执行后的内存是否回到稳定水平，是否发生持续下降。

当前已用独立 C++ 程序验证世界包及中国包的瓦片 CRC、独立标注和名称搜索，包括中国包超过 21 GB 的读取偏移。追加验证覆盖损坏的头/目录/像素 CRC、包数量上限、分配失败、介质切换、搜索分批重试/取消及像素预算回收。固定 LVGL 9.4.0 的 RGB565/RGBA 实际渲染测试和原有 PNG、地图队列回归均通过；ESP32-S3 `tlora_pager_sx1262` 固件也已完成成功构建。这些不能替代上述真机内存验证。
